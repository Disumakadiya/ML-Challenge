# M2_E5 — TF-IDF name/address blocking + LightGBM pair matching

Sparse blocking for business entity resolution. Source 2 and Source 3 are indexed as one
candidate universe; each Source 1 record retrieves Top-K candidates from two independent
TF-IDF channels, the union becomes the candidate set, and a LightGBM model scores those pairs.

## Approach

**Two TF-IDF channels.** One matrix over normalized `business_name`, one over normalized
`business_address`. Both are L2-normalized so the dot product is cosine similarity, and both
carry IDF weights computed over the full indexed universe.

**Blocking recall is the ceiling.** The ranker's quality only matters if the true match is in
the candidate set, so retrieval runs at the largest swept K once and every smaller K is derived
from the per-channel ranks rather than re-queried.

**One retrieval pass, many models.** `TfidfBlockingIndex.retrieve` is called once at `k_max`;
`CandidateBatch.restrict_to_k` rebuilds the union of Top-K retrievals for any smaller K without
touching the index again. One LightGBM model is fit per K, and K is selected on a deterministic
match-count-stratified holdout by macro F0.5.

**Features.** 21 per pair: 14 shared entity-resolution features reused from M2_E4 (excluding
every `pass_*` placeholder) plus 7 blocking features from this experiment — the two TF-IDF
cosine similarities, the retrieval rank and its per-channel ranks, and the two channel
indicators.

## Data contract

| Requirement | Behaviour |
|---|---|
| Candidate IDs | Original `S2-`/`S3-` IDs, never re-encoded |
| Source identity | Preserved per candidate; open-set country is a feature, not a filter |
| Memory | Sparse and batched; peak memory follows batch/block sizes, not corpus size |
| Test coverage | Every test Source 1 ID appears exactly once in both output files |
| Predictions | Drawn only from that row's retrieved candidates |
| Headers | `source1_entity_id\tcandidate_entity_ids`, `source1_entity_id\tmatched_entity_ids` |

## Running it

The dataset may be local or in S3. S3 inputs are staged onto local disk once, because the store
builder seeks through the TSVs and the ground-truth index memory-maps byte offsets computed from
them — both need real seekable files, not a streaming object handle. Staged files are reused
across runs.

```bash
# local
python -m experiments.M2_E5.run_experiment \
    --data-root . \
    --k-values 5,10,20,30,50

# S3
python -m experiments.M2_E5.run_experiment \
    --train-dir s3://my-bucket/ml-challenge/student_resource/dataset/train \
    --test-dir  s3://my-bucket/ml-challenge/student_resource/dataset/test \
    --stage-dir /mnt/workspace/s3_stage \
    --workers 31

# final submission
python -m experiments.M2_E5.run_experiment \
    --final-inference --workers 31 \
    --submission-dir output
```

On SageMaker AI Studio, `notebooks/member2/M2_E5_tfidf_name_address.ipynb` drives the same CLI
through subprocesses, so the multi-gigabyte store and the LightGBM models are released between
stages instead of accumulating in the kernel. It does not run final inference unless you flip
`RUN_FINAL_INFERENCE`.

## Outputs

Written to `--output-dir` (default `experiments/M2_E5`) and git-ignored, because every one of
them is regenerated by a run:

| File | Contents |
|---|---|
| `metrics.json` | Everything, including `selected_k` and the per-K `per_k` block |
| `config.json` | The fully resolved configuration of the run |
| `candidate_pairs.tsv` | Validation-fold candidates at the selected K |
| `matching_results.tsv` | Validation-fold predictions at the selected K |

These two TSVs are **validation** artifacts, not the test submission. Final inference writes the
submission pair to `--submission-dir` instead. Read `metrics.json` for the numbers: `per_k[k]`
carries `blocking_recall` (the ceiling on ranker quality — the model can only score pairs
retrieval surfaced), `macro_f0_5` (the selection criterion), micro precision/recall, and the
candidate-count distribution.

## Performance

Retrieval dominates, and it is embarrassingly parallel over query batches: every worker
memory-maps the target store read-only and scores its own batches, so the target side is never
copied or pickled. `--workers 0` (the default) uses every core but one.

Two things determine throughput:

- **Source 1 frames must be wider than one query batch.** `retrieve` splits its frame back into
  `query_batch_rows` batches and only then farms them out. The runner gathers
  `query_batch_rows x min(workers, 8)` rows per call, capped at the read chunk, so the pool
  actually has work to distribute. Lower `workers` first if you hit memory pressure — that knob
  scales peak memory linearly and runtime inversely.
- **Peak memory** is the in-flight similarity blocks:
  `workers x query_batch_rows x target_block_rows x 4 bytes` (~32 MB per worker at the
  defaults), plus ~1.3 GB of CSR for a full 10.3M-row S2+S3 store.

Measured on the real training data with a 200,000-row target cap: 230 queries/s single process,
and the process pool cut a 4,096-query pass from 33.5 s to 16.4 s on 12 cores. The full
S2+S3 universe is 10.3M rows, so the store build itself takes roughly 15 minutes per split;
retrieval time then follows the core count.

## Options

| Flag | Default | Purpose |
|---|---|---|
| `--data-root` | `.` | Project root, or an `s3://` prefix |
| `--train-dir` / `--test-dir` | derived | Local or `s3://` dataset directories |
| `--stage-dir` | `<output>/../m2e5-s3-stage` | Where S3 inputs are staged locally |
| `--workers` | `0` | `0` = all cores but one, `1` = no multiprocessing |
| `--query-batch-rows` | `1024` | Queries per worker task |
| `--target-block-rows` | `8192` | Target rows per similarity block |
| `--k-values` | `5,10,20,30,50` | K sweep; `k_max` drives the single retrieval pass |
| `--k` | `max(--k-values)` | Fixed K for final inference |
| `--max-target-rows` | none | Cap indexed S2+S3 rows for quick runs |
| `--chunk-size` | `20000` | Read chunk for streaming |
| `--threshold` | `0.5` | Probability above which a candidate is predicted |
| `--smoke-test` | off | End-to-end run on a small dataset derived from the real files |
| `--final-inference` | off | Fit from training data and write the submission TSVs |

`--max-target-rows` takes a **prefix** of the target files, so it is a speed knob for
iterating, not a way to get a meaningful score: a truncated universe drops the true match and
collapses recall.

## Smoke mode

`--smoke-test` derives a small dataset from the real files that *keeps genuine matches* — every
Source 1 row and its true candidates are preserved — and pads it with filler rows, then runs
the whole pipeline in a temporary directory that is deleted afterwards. Preserving real matches
matters: capping the target universe instead produces zero positives and a misleading failure.
